## 利用者のタスクと画面の設計

設計を判断する本人が、重複時にどのルールが勝つか、解除がいつ終わるか、保存と適用結果がどう異なるかを理解できることを目的とします。

現行ホームの緑・背景・書体の方向性を引き継ぎ、宣伝文よりも現在の模擬時刻・設定・反映状態を優先。操作は「対象アプリ」「時間帯ルール」「シナリオ」の順にまとめています。スマホ幅では一列、広い画面ではシナリオと障害設定を横に配置。HTMLの入力・dialog・ボタンを使用し、選択状態、破棄確認、確定前の影響説明を提供します。

## 最初の体験

1. 「認可を体験する」→模擬許可→「確認して制限を開始する」。許可だけでは再開しません。
2. YouTubeの「一時解除を試す」→サンプル理由を入力。空白のみでは確定できません。
3. 終了予定を確認して解除。「1分進める」で残り4分、「5分進める」で期限後の再評価を確認。
4. 「仕事の時間」を編集し、対象・曜日・時刻・解除条件・優先順を変更。「次へ」で重複と影響を確認して反映。
5. 取消では破棄確認。アプリ切替の代わりに別の場所を見ても画面メモリの値を維持しますが、再読込では初期化します。

理由はサンプルを使い、個人情報や実際の解除理由を入力しないでください。外部送信・localStorage・Cookie保存は追加しません。本文・操作記録・grantは直近30件に制限したメモリ内モックです。

## シナリオと判断すること

各シナリオを選択すると体験の状態を初期化します。模擬時刻は月曜12:00を基準とし、自動では進みません。反映の待機約0.8秒はUI説明用です。

| シナリオ | 操作と観察 |
| --- | --- |
| 01 理由入力 | 理由の空欄拒否、取消、5分解除、再表示でも同じ期限 |
| 02 優先切替 | YouTubeを5分解除しようとしても、12:02の上位ルール開始までの最大2分。境界後は一時解除不可 |
| 03 夜のダミー課金 | 月曜22:00へ進み、仮の100/300/500円を選択。実際の請求なし |
| 04 適用失敗 | 解除や設定変更を確定すると失敗。保存した設定は保持。「次の模擬結果」を成功に戻し、本人が再試行 |
| 05 期限登録失敗 | 解除要求後、期限イベント登録に失敗した想定を表示。解除しない対応仮説を比較 |
| 06 再認可 | 取消でルール保持・grant無効化。再許可しても本人が再開するまで停止 |

「結果保存前に中断」を選ぶと結果不明を体験できます。同じ対象へ別の解除を連打しても未確定grantを重複付与しません。再試行は元の絶対期限を維持します。状態モデルは少数の直列操作用で、最後の操作に対する再試行のみを提供します。

## 投稿済みレビューへの対応仮説

これらはPR #36で採用された修正ではありません。Web上の選択肢として体験する仮説です。

- **P1**: 期限登録失敗の想定では新たな解除を行わない。OS予定の登録順序・取消・ロールバック・実機での保証は実装していません。
- **P2**: 解除中に未来の優先切替が早まる場合、次の境界までに期限を短縮。保存前に旧終了・新終了を表示して本人確認。期限の延長と失効grantの復活はしません。

P2の再現: 01からYouTubeを5分解除→1分進める→「短い集中」を編集し有効化、開始12:03、優先順位1番目→次へ。解除期限が12:05から12:03へ短縮されることを確認して保存します。

## デモに含めないもの

実際のFamilyControls/ManagedSettings/DeviceActivity、Swift・Extension、SQLite/2DB/outboxの永続化、File Protection、容量80/100MiBの制御、OS kill後復元、DST・タイムゾーン移動・端末時計変更・バックアップ。本体終了中の期限後再制限はWebで証明しません。

週間ルール・前日開始の日跨ぎを模擬カレンダーで評価します。終了が開始以前なら翌日、同時刻なら24時間というUI説明付きの体験値です。対象アプリ名・プリセット・模擬金額は固定サンプル。履歴一覧は状態理解の補助で、製品の初版に履歴画面を必須化する判断ではありません。
