# 「あなたの選択の記録」改善案と共有UIデモ

本人依頼 / #206。`demo/choice-history`、共有基盤PR #203（8306777）に依存する限定UIデモ。main 0c2ec4eまでの差分では本画面の変更なし。アプリの本体画面・Providerを使い、fixtureだけをWeb demoへ注入する。Swift・DB・bridgeの変更ではない。

## 現状の確認

`HistoryScreen` / `HistoryReasonScreen` / `HistoryProvider` とhistoryVersion1を照合した。

- 操作一覧: 理由保存、確定前取消、ルール変更、一時解除要求、再試行、再開、停止というactionと、受付/予定登録/反映/完了/失敗/未確認/期限終了などの状態を表示。
- 秒単位の日時、grantの状態、記録上の期限、削除済みの理由も表示。実利用時間や現在の制限の測定ではない。
- 操作と理由の別index、日付のYYYY-MM-DD手入力、前後40件、取得時刻/timezone、欠損/取込状態、容量への導線がある。
- 理由本文は一覧に含めず、選んだcommandの1件だけを別画面で読む。準備のみ/受付あり/欠落/削除などの区別がある。
- **アプリ名/当時の対象表示/ルール名/目標/当初希望した分数はHistoryRowにない。現在のホームsnapshotから過去を復元することはできない。** expiresAt−row.atも実際の利用時間ではなく、当初希望した長さの代用にもできない。

困る点は、本人の「何を選び、なぜそうしたか」より内部処理の語彙が前に出ること。同じcommandの関連eventが別カードになり、技術情報が一覧より先に並ぶ。日付入力にも形式の知識が必要。欠損・失敗の区別とprivate reasonの保護は維持する。

## この画面の役割

振り返りの量（累計/週月の時間）と、選択の文脈を分ける。この画面は過去の選択を責めたり採点せず、次の時間の使い方を自分で考える材料を届ける。

| 情報 | 一覧 | 1件の詳細 | 現行データ |
| --- | --- | --- | --- |
| 日付・記録時刻 | 日付見出し＋時刻 | 記録日時 | あり。選択の瞬間と処理更新時刻を同一視しない |
| 当時の対象アプリ | 見出し | 対象が分かる見出し | 不足。デモの保存案portでのみ供給 |
| 選択と結果 | 平易なタイトル＋状態 | 保存のみ/受付/未確認/期限/取消等を区別 | action/status/grantStatusを変換。実際に使ったとは言わない |
| 自分の理由 | 本文を自動取得しない | 選んだ1件を全文表示 | 既存reason API。削除/欠落/未確認を空文としない |
| 当時のルール・目的 | 詳細へ | 当時の目的を穏やかな引用面で表示 | 不足。現在設定を流用せず、保存案としてのみ表示 |
| 希望した分数 | 詳細へ | 希望と記録上の上限を区別 | 分数は不足、expiresAtはあり。実使用時間はなし |
| 処理経過・取得情報 | 欠損/未取込は常時通知。詳細情報は開示 | 関連eventは開いて確認 | ページ内だけで確認。完全な経過と断言しない |

## 画面設計

1. 振り返りタブの上部に「選択の記録を見る」。時間集計が未提供でも、確認できる記録へ進める。時間集計や成果を架空の値で埋めない。
2. 一覧は「操作と結果／保存した理由」のindex切替と、日付カレンダー/今日/前日/翌日/全期間。kindは既存APIの区分であり、取得ページをローカルfilterして全件の結果と装わない。
3. 日付ごとに対象・選択・結果。関連commandは**表示中の最大40件の範囲で**まとめ、最新の処理事実を代表にする。時刻も「記録」と明示し、最初の選択時刻を推測しない。次のページに同じcommandの記録が続く可能性は残る。
4. タップで「選択の詳細」。当時の目的→自分の理由→希望/上限/結果→必要なら処理の補足。理由本文の読み込みはこの操作の後だけ。取消/設定変更等の理由がない記録にも詳細を用意する。
5. 前後ページは一覧の後。取得時刻/zone/保存状況は開示へまとめる。欠損・未取込・失敗を隠すためには使わない。

原則1/2/4/5、U03/U06/U07、UI22/UI23/UI24/UI25/UI26/UI35/UI36と、history-recordsのprivate read/削除/取得世代の保護を参照。未確認を成功とせず、理由や目標を採点しない。色・文字・余白は既存GraphiteColors/FlowScreenを共有する。

## デモの当時情報と本体との差

`HistoricalChoices` は、記録の不透明な参照に紐づく提案用の任意port。通常の本体では未供給で、**不足した情報は不足と表示**する。デモではfixtureにだけ、アプリlabel・当時のルール/目標・希望分数をimmutableに保持する。現在のルールを改名しても履歴の文脈は変わらない。理由削除では本文を消し、履歴/全記録削除ではこのfixture文脈も消す。

これはnative履歴の拡張を実装した意味ではない。正式採用前に#206等で次を設計する。

- 当時の対象の保存/表示方法。Appleの実名/tokenをJSやログへ出す前提にしない。許可取消/対象再選択/アプリ削除時の代替表示と、nativeで識別表示できる範囲を確認。
- ルール名/目標/希望分数/必要なら最初の選択日時のimmutable保存、版、移行、削除範囲、保護/バックアップ。本文を複製・拡散しない。
- 一つの選択と後続の処理を全件でまとめるquery/ページ境界、理由保存と共有受理の関連、日付filterが何の日時を対象とするか。既存40件の便宜的なgroupを完成したquery契約にしない。
- 新しい文脈をprivate情報として取得世代・削除・foregroundに結びつける。新しいデータ契約とUIをレビューしてからnativeへ接続する。

現データだけでも、新UIのレイアウト・日付選択・状態の伝え方・詳細と補足の分離を使える。サンプル名が表示できることを、本物の履歴から対象を復元できた証拠にはしない。

## デモの試し方

`demo.config.json` のstudy=historyをデモbuildへ渡す。native/通常Webの接続を切り替える設定ではない。`npm run demo:package` とdemo/**のpushで既存CIを使う。ローカル開発では `EXPO_PUBLIC_ITOMA_DEMO_STUDY=history npm run demo:web`。

- ホーム→振り返り→選択の記録を見る。過去の架空データ（保存のみ/解除/未確認/取消/ルール変更）が初めから入っている。
- Xを開く→理由・当時の目的・希望/上限・結果を見る→補足の関連eventを開く→戻る。
- カレンダー/前日/全期間を試す。「保存した理由」では理由だけの保存も確認。
- 上部のデモ操作で「現行の項目だけで表示」と「当時情報の保存案で表示」を比較。「記録のない状態」も試せる。切替は入力/記録を消す確認を経てdocumentを再読込する。
- 実際に一時解除をデモ操作すると、同じsessionの記録に追加される。保存名を編集しても過去の文脈は変更しない。
- 設定から理由を削除して戻り、本文が再表示されないことを確認する。

理由・サンプルはタブ内メモリーのみ、通信/URL/log/Web Storageへ送らない。/history-reasonも本文やIDをURL paramsへ載せない。デモ用のsample/empty/context切替はWeb demo build内だけ。

## 追加比較：タイムライン型（本人追加依頼）

同じ記録を新しい順に縦線とカードで表示する比較案を追加。日付の見出し→記録時刻→対象/選択→当時のルール→状態→希望分数/記録上限→詳細への入口、の順で確認する。日付ごとに線を区切り、線の長さ・カード間隔は経過時間や継続利用を表さない。処理ログを一つずつ増やさず、一覧と同じページ内command集約を使用する。

- Webデモの上部「履歴の表示案」で **タイムライン／一覧** を切替。今回の比較ではタイムラインを初期表示とする。切替でquery・選択中の日付・session・入力/記録を再生成しない。詳細から戻っても表示案を維持する。
- 比較操作はWebのbanner内だけ。本体には表示設定を新設しない。任意のHistoryPresentation contextが未供給の本体は従来の一覧を表示する。画面・データ取得・詳細は共通のまま。
- 理由本文はカードに自動展開しない。カードを選んだ後に既存の詳細で1件だけ読む。削除/取消/未確認/不足情報は一覧と同じ扱い。当時情報の保存案・現行項目だけ・記録なしの比較も両表示で確認可能。
- 一覧は多くの記録を探しやすく、タイムラインは一つずつの選択と結果を追いやすい。タイムラインのカードは縦に場所を使うため、比較後に採用を判断する。新しい永続化・成果集計・native契約を採用した意味ではない。

## タイムラインの継続読込（本人追加依頼・#206）

本人はタイムライン型を選択。既存v1の40件keysetを使い、末尾0.6画面手前で過去のmetadataを追加取得するレビュー用UIを追加した。API/Swift/DB/サーバーは変更しない。Webデモは長い架空履歴を初期状態にする。上部シナリオの「長い履歴でスクロールを試す」「過去の記録サンプル」「記録のない状態」で比較できる。

- FlatListを画面の唯一の縦スクロールとして使い、見出し/日付条件はheader、保存状況等はfooterに置く。ScrollViewの中にFlatListを入れない。カードの描画を仮想化し、理由本文は引き続き選択した1件だけ読む。
- 最初のページのrevision/zoneと次のcursorを渡す。同じcursorを同時に要求しない。成功したページだけ追加し、keyを重複表示せず、関連commandは読み込んだ範囲でまとめる。完全な選択queryとは宣言しない。
- 追加読込中も前のカードを残す。失敗後は自動再試行を止め、明示的な再読込ボタンを出す。読み込みが進まないcursorも止める。最後は「この範囲の記録はここまでです」。手動の「過去の記録を読み込む」も用意する。
- 途中でrevision/zoneが変わった場合はページを混ぜず、表示済みの範囲と選択を消して「最新の記録を確認する」へ。日付/kind変更・削除・source変更・foreground再取得でも旧応答を棄却する。refreshはタイムラインの先頭へ戻る。
- 詳細へ進むと追加読込を止め、選んだrowは読み込んだ範囲内で確認する。戻る際は不要な再読込をせず、ページとFlatListを保持する。背景では理由を閉じ、foregroundで先頭から現在の世代を読む。
- 一覧の比較案は従来の40件置換型。Webの表示切替を本体の設定として追加しない。本体のcontext未供給時は一覧のまま、タイムラインの正式接続はPR採用時に判断する。

描画の仮想化と、取得済みmetadataの保持は別。metadataはスクロールして読み込んだ範囲だけRAMに保持し、日付/更新/削除等で破棄する。全件を初回取得・永続化しない。数万件までのRAM推移やページ窓の上限、VoiceOver/Dynamic Type、iOSでの復帰位置/スクロール性能は未検証で、仮想化だけで一定メモリーを保証しない。
