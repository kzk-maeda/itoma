# ルールと解除ログによる時間集計の確認

関連 #98、[ADR0012](../adr/0012-rule-log-time-aggregation.md)。新Swift/JSを含むbuildが必要。これは設定と操作ログからの算出で、OS遮断の継続実測とは区別する。

1. source SHA / build ID / JS SHA / native config・host/Extension一致、端末/OS、JST日時を記録する。既存の通常ルールを使い、PoC専用storeを混ぜない。
2. ルールを保存し、開始前に一度現在状態を表示する。例: 20〜24時、対象A/B。21:00からAを5分解除し、24時以降に振り返りを更新する。ルール/停止等に変更がなくログが揃えば、累計増分・週/月・日別の対応範囲は3時間55分。Bが制限を続けても解除5分を戻さない。
3. 短い確認では10分ルールの途中に1分解除（9分）、解除なし（10分）も使う。端末をロックして本体を閉じるケースと、開いたままのケースを分ける。
4. A/Bの解除を2分ずらして各5分行う。重なる3分を二重控除せず、7分控除になることを確認する。2分で早期終了した解除は2分だけ控除する。
5. 解除要求の取消/登録失敗を成功解除として控除しない。成否不明ならその解除候補期間だけがpartialになる。開始/終了の認可unknownが出ても、設定/操作ログが揃った区間全体は消えない。
6. 途中の停止/resume、終了短縮/延長、曜日/日跨ぎ、対象/優先順の変更を試す。変更前の時間を現在のルールで書き換えず、変更時刻で計算が切り替わることを確認する。
7. 更新後の累計を控えて週/月を切り替える。上部累計は変わらず、期間合計は同じtoken/as-ofに対応する。再更新時だけ新しいas-ofになる。
8. 既存記録のある端末で新buildを開く。既存のルール・解除ログの保持範囲から再計算され、現在設定だけで記録開始前を埋めないことを確認する。UI見出しは「ルールから計算した時間」。
9. 全記録削除で累計を消し、旧batch/古い画面/tokenで復活しないことを確認する。理由・選択履歴だけの削除では時間を残す。

集計不一致時は、予定・変更/停止時刻・解除の成功/終了・ログの取込/欠損を確認する。個人のtoken/理由/生DB・署名情報を公開Issueへ貼らない。ログを失った過去の4時間を自動で235分へ直せるとは保証しない。
