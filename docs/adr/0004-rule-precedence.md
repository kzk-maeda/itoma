## 背景

仕事中と夜でルール別の厳しさを選びたい。日跨ぎは開始日の曜日、端末現地時刻、初期解除5分/上限30分は利用者回答で決まっている。重複時の具体的な優先方式は提案を求められている。

## 選択肢と比較

| 案 | 評価 |
| --- | --- |
| 暗黙に厳しいモード優先 | 本人の提案確認要求と合わず、モードの序列も未合意 |
| 新規rule優先 | 既存の意図を弱める可能性 |
| rule対ごとの優先 | 柔軟だが循環・矛盾が起きる |
| **全ruleの一意な優先順を提示・本人確定** | 対象ごとの勝者が決まり、競合を説明できるため推奨 |

## 提案

週次の[開始,終了)区間を現地暦で評価する。優先順はrule全体のtotal orderとして保存。重複を保存前に提示し、既存優先を候補として本人が確認する。grantは現勝者の現occurrenceのみ有効。次の勝者切替までの有効時間を事前に示し、失効後は復活させない。P2修正として、現在の勝者/versionが同じでも未来の切替を比較し、短縮前に旧/新期限の確認を得る。effectiveExpiresAtをUI/登録予定と揃え、新予定登録前には候補編集を有効化しない。

詳細仕様の正本は [rules.md](../system/rules.md)。採用前にコードの確定仕様と扱わない。

## 影響・限界

日跨ぎ、DST、時計変更、優先切替をR01〜R14で検証する。待機/回数制限なしは了承済み。DST解決方針、最小1分、共通のデフォルト時間設定等の細部は本PRのレビュー対象であり、個別に了承された事項とは区別する。時計改ざん防止やOSイベント時刻の精度は保証しない。

## 証拠と採用条件

Issueの利用者回答とPR上の7項目の了承を根拠とする。P1/P2の修正は今回の了承で解消済みとはせず、再レビュー待ち。OS APIの現行仕様と端末条件は [PoC計画](../system/poc-plan.md) で確認する。提案の採用と実機での成立を分け、失敗したら範囲/方式を見直す。比較対象のAPIを実装済み・動作済みと記載しない。

## 再検討条件

対象ごとに逆のrule優先が必要、OSの予定制約でこのモデルが実現できない、境界で本人の予想と異なる解除終了が頻発する場合。
