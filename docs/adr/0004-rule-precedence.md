# 0004: 日跨ぎは開始日、重複は本人が確定した優先順で評価する

- 状態: **Proposed**（人間の比較レビュー・採用待ち）
- 検討Issue: https://github.com/kzk-maeda/itoma/issues/23
- 決定PR: https://github.com/kzk-maeda/itoma/pull/36 （比較レビュー中・採用未決定）
- 採用日: 未定
- 検証状況: 設計上の検討のみ。純粋ロジックのテスト仕様を作成、実装・実機は未検証
- 関連ADR: [0002 MVP](0002-mvp-scheduled-restrictions.md)。0003〜0006は同じ設計PRの相互依存する提案

## 背景

仕事中と夜でルール別の厳しさを選びたい。日跨ぎは開始日の曜日、端末現地時刻、初期解除5分/上限30分は利用者回答で決まっている。重複時の具体的な優先方式は提案を求められている。

## 選択肢と比較

| 案 | 評価 |
| --- | --- |
| 暗黙に厳しいモード優先 | 本人の提案確認要求と合わず、モードの序列も未合意 |
| 新規rule優先 | 既存の意図を弱める可能性 |
| rule対ごとの優先 | 柔軟だが循環・矛盾が起きる |
| **全ruleの一意な優先順を提示・本人確定** | 対象ごとの勝者が決まり、競合を説明できるため推奨 |

## 提案

週次の[開始,終了)区間を現地暦で評価する。優先順はrule全体のtotal orderとして保存。重複を保存前に提示し、既存優先を候補として本人が確認する。grantは現勝者の現occurrenceのみ有効。次の勝者切替までの有効時間を事前に示し、失効後は復活させない。

詳細仕様の正本は [rules.md](../system/rules.md)。採用前にコードの確定仕様と扱わない。

## 影響・限界

日跨ぎ、DST、時計変更、優先切替をR01〜R10で検証する。DST解決方針、最小1分、共通のデフォルト時間設定、待機/回数制限なしは追加提案であり、利用者回答そのものではない。時計改ざん防止やOSイベント時刻の精度は保証しない。

## 証拠と採用条件

Issueの利用者回答を根拠にした設計判断。OS APIの現行仕様と端末条件は [PoC計画](../system/poc-plan.md) で確認する。提案の採用と実機での成立を分け、失敗したら範囲/方式を見直す。比較対象のAPIを実装済み・動作済みと記載しない。

## 再検討条件

対象ごとに逆のrule優先が必要、OSの予定制約でこのモデルが実現できない、境界で本人の予想と異なる解除終了が頻発する場合。
