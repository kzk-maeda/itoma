# 0003: 設定・認可・一時解除・OS観測を独立した状態として扱う

- 状態: **Proposed**（人間の比較レビュー・採用待ち）

- 決定PR: https://github.com/kzk-maeda/itoma/pull/36 （比較レビュー中・採用未決定）
- 採用日: 未定
- 検証状況: 設計上の検討のみ。純粋ロジックのテスト仕様を作成、実装・実機は未検証
- 関連ADR: [0002 MVP](0002-mvp-scheduled-restrictions.md)。0003〜0006は同じ設計PRの相互依存する提案

## 背景

単一フラグなら画面は簡単だが、設定保存成功とOS反映失敗、期限切れと再制限失敗、認可喪失を区別できない。利用者は設定保持・明示的な再試行・絶対期限・再認可後の確認を求めている。

## 選択肢と比較

| 案 | 評価 |
| --- | --- |
| 単一isBlocked | 状態矛盾を隠し、失敗復旧や本人の意図を表せない |
| 全イベントから再構築するevent sourcing | 追跡性は高いがsnapshot/移行/再生のコスト増 |
| **版付きsnapshot＋command/grant＋独立したOS観測** | 必要な状態・履歴を明示し、実機観測の限界も表現できるため推奨 |

## 提案

確定policyと画面draftを分離し、global revisionで更新競合を拒否する。grantは対象・ruleVersion・occurrenceと絶対終了日時を持ち、再試行で延長しない。command受理/結果、観測の鮮度・証拠を分ける。履歴は監査用で、ドメイン状態の再構築の唯一の正本にはしない。

詳細仕様の正本は [domain-model.md](../system/domain-model.md)。採用前にコードの確定仕様と扱わない。

## 影響・限界

DTOと状態数は増えるが、未適用を成功表示する誤りを避ける。次境界を過ぎた観測を古いものと扱う。本体終了時のOS再制限は別PoC。状態モデル/遷移表のD01〜D12を実装テストへ渡す。

## 証拠と採用条件

Issueの利用者回答を根拠にした設計判断。OS APIの現行仕様と端末条件は [PoC計画](../system/poc-plan.md) で確認する。提案の採用と実機での成立を分け、失敗したら範囲/方式を見直す。比較対象のAPIを実装済み・動作済みと記載しない。

## 再検討条件

OS側で観測可能な情報が想定より少ない、grantの束縛が利用者体験と合わない、イベント保存が状態の正本より複雑になる場合。
