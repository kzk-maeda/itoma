## 背景

仕事中と夜の無意識なX/YouTube利用を減らし、調べ物や休憩時の例外は本人が決めたい。要望は [Issueコメント](https://github.com/kzk-maeda/itoma/issues/21#issuecomment-6630426591) と2026-11-04 JSTのチャット回答による。

## 選択肢と判断

| 選択肢 | 利点 | 不採用・後続とする理由 |
| --- | --- | --- |
| 手動制限だけ | 小さなPoCに適する | 仕事中・夜の繰り返しという利用場面を十分に満たさない |
| 編集可能な時間帯＋ルール別の3つの挙動 | 場面ごとに本人が厳しさを選べる | 採用提案。OSイベント・一時解除の実機検証が必要 |
| 全ルール共通の1つの挙動 | 設計は単純 | 仕事中と夜で挙動を変えたい要件を満たさない |
| 本体からも変更できない厳格ロック | 制限を迂回しにくい | 本人がいとま側で制御できる合意と矛盾する |
| 初版から実課金・分析・達成演出 | 機能は増える | 利用者が初版不要と明示。実決済は対象外 |

## 提案

詳細仕様は [MVP仕様](../system/mvp.md) を正本とする。

- 本人が対象アプリを追加・編集できる。
- プリセットの曜日・開始・終了時刻を編集できる。
- ルールごとに理由入力／ダミー課金／一時解除不可を選べる。
- 一時解除不可でも、いとま側の設定編集・停止は可能とする。
- 実際のアプリ制限を必須とし、理由入力場所と一時解除期間は変更可能とする。

## 影響と未解決事項

#22の状態モデルはルール別解除条件と希望/適用結果の分離を必要とする。#23は重複・日跨ぎ・解除期限を決める。#16のダミー課金は請求を発生させず、操作前に模擬と明示する。#17の分析・詳細履歴を初版必須にしない。#26ではJS停止中の再制限を検証する。

日跨ぎの曜日帰属、プリセット内容、入力条件、秒数、回数、正式名称、保存形式はこのADRで決めない。採用しても実機合格とはしない。

## 再検討条件

OSで対象制限や期限後の再制限が成立しない、解除導線が設計できない、利用者が設定・解除条件を理解できない、複数ルールの競合が意図しない制限を生む場合。証拠を関連Issueへ記録し、範囲変更は改めて合意する。
