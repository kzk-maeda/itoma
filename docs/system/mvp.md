# MVP仕様

状態: **利用者との合意を反映したレビュー案**。検討Issue: [#21](https://github.com/kzk-maeda/itoma/issues/21)。正式な仕様採用は決定PRのレビュー・mainへのマージで確定します。実装・OS動作の検証済み宣言ではありません。

判断理由: [ADR 0002](../adr/0002-mvp-scheduled-restrictions.md)。要望の出典: [利用者コメント](https://github.com/kzk-maeda/itoma/issues/21#issuecomment-6630426591) と、その後のチャットでの確認（2026-11-04 JST）。

## 解決する利用場面

- 平日の仕事中に無意識にXやYouTubeを開いてしまう。
- 仕事後の夜、何気なく開いたアプリで時間を使い、読書などに使いたい時間を失う。
- 調べ物や明確な休憩では、本人が選んだ条件で一時解除したい。

## 初版に含める範囲

| 機能 | 合意した範囲 | 残る設計・検証 |
| --- | --- | --- |
| 対象選択 | 本人が制限対象アプリを選択し、追加・編集できる | FamilyActivityPickerの取得・表示範囲。カテゴリ・Webサイトは初版必須に含めず、必要なら追加判断 |
| 時間帯ルール | プリセットから選び、曜日・開始・終了時刻を編集できる | 初期プリセット、日跨ぎの曜日帰属、重複・時差は #23 |
| ルール別の挙動 | 理由入力で一時解除／ダミー課金で一時解除／一時解除不可を、ルールごとに選ぶ | 正式名称・入力条件・模擬課金の具体操作は #22/#23/#16 |
| 本体での制御 | 一時解除不可のルールでも、いとま側で設定を編集・停止できる | 複数ルールが同じ対象に効く場合の結果は #23 |
| 一時解除 | 調べ物・休憩のために利用。実際のOS解除を伴う | 入力画面の場所と期間は変更可能。期限後再制限は実機PoC必須 |
| 設定の保持 | 再起動後にも選んだルールを扱える本実装を目指す | 保存方法と復旧・OS適用との整合性は #25 |

「平日21:00〜26:00」は利用者の例で、固定プリセットの仕様ではありません。26:00を翌日02:00として扱う表現を想定しますが、金曜夜から土曜02:00を含むか等の曜日帰属はまだ合意していません。#23で決めます。

「一時解除不可」は、制限対象アプリからの一時解除を許さない意味です。いとま側のルール編集・停止を禁止したり、本人が変更できない強制ロックを作ったりしません。設定変更で本当に制限が解除されたかは、他の有効ルールとOS適用結果も確認して表示します。

## 対象外

傾向分析、時間を取り戻した達成演出、実決済・StoreKit・商品登録・料金徴収、バックエンド・独自認証・Android対応。初版のダミー課金は実際の請求がないことを操作前に明示します。全アプリ起動情報の取得や他社アプリ内の画面限定制限は約束しません。詳細な履歴機能は初版必須ではなく、正しい状態表示・復旧に必要な最小記録と分けて後続判断します。

## 受入シナリオ

| ID | 操作 | 期待結果と検証条件 |
| --- | --- | --- |
| MVP-01 | 説明を読んで認可する／拒否する | 拒否しても戻れる。未認可を制限有効と表示しない。iPhone実機で確認 |
| MVP-02 | 対象アプリを選択・追加・編集し、反映／取消 | 反映した対象だけに適用。取消で確定設定を変えない |
| MVP-03 | プリセットの曜日・時間帯・挙動を編集 | ルールごとに値を保持し、適用期間と例外を事前に理解できる |
| MVP-04 | 制限時間内に選択アプリを開く | 実際にOSが制限する。モック・Web画像を実機成功と扱わない |
| MVP-05 | 理由入力／ダミー課金の一時解除を選ぶ・取消 | 確定前に条件・期間と実請求なしを説明。取消では解除を付与しない。具体条件は後続設計 |
| MVP-06 | 一時解除不可の対象を開く／いとま側で編集・停止 | 対象側では一時解除不可。本体から設定を制御できる。競合がある場合の結果を正直に示す |
| MVP-07 | 一時解除後に本体を終了し、期限を迎える | OS主導の再制限が成立するか #26 で確認。未成立を完了扱いにしない |
| MVP-08 | 権限取消・保存失敗・適用失敗・再起動 | 希望設定と観測できたOS状態を区別。原因と次の操作を示す |

各UIのLight/Dark、文字拡大、VoiceOver、Reduce Motion、操作後の結果とフォーカスを確認します。Simulator・Web・実機の証拠を分けて記録します。

## 譲れない目的と変更可能な手段

- 譲れない: 本人が選んだアプリを実際に制限できる。
- 変更可能: 解除理由の入力画面の場所、一時解除の時間。
- 技術判断待ち: 本体終了中の期限後自動再制限。できなければ勝手に本体常駐を要求したり機能を削ったりせず、PoC結果を示して仕様変更を相談する。
