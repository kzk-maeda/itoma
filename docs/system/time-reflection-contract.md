# 制限を続けた時間の累計・週月集計契約案

状態: **本人の計上方針を反映したProposed / #96の詳細契約レビュー中**。本人は「実際にアプリを制限して自分の時間を過ごせた時間を記録したい」「一時解除時間は累計に含めない」と指定した。旧案の設定時間集計・解除非控除は取り下げる。固定累計＋週次/月次という了承済み構成を維持し、制限を続けた時間を穏やかに振り返れるようにする。操作履歴 #57/#132 と、記録 #97・集計 #98・画面 #99・統合 #100 を区別する。製品実装・実機合格の宣言ではない。

## 1. 計算の定義と例

計算の入力は、nativeが耐久commitしたpolicy/対象の有無/Activation/contextに加え、**制限の適用確認と解除/再制限の遷移**、記録coverage。`RuleEvaluator`相当の採用済み曜日・日跨ぎ・DST規則をnative側で使う。TSに勝者や別集計式を作らない。

1. policy/Activationのfactから候補範囲を作り、次factまたはsnapshotのas-ofで切る。記録開始より前と未来を除く。点の設定観測から実遮断区間を生成する手順ではない。
2. enabledのrule/対象/Activationから予定区間を展開し、後述のqualificationを満たす制限区間と交差する。編集前の設定や未適用の予定を延ばして使わない。
3. 一時解除の区間のunion、停止/未適用、gap/削除/未確定区間を除外する。残ったUTC半開区間のunionを取る。
4. 正確な秒数を合計し、表示時だけ時分へ丸める。アプリ数倍にせず、重なる解除も一度だけ除外する。丸めた日別値を足さない。

全体累計は実時間の1本の指標とする実装案。A/Bを制限してAだけ一時解除した場合も、その解除区間は全体累計から除外する。Bの制限継続は操作/状態の事実として保持し、Bが残ることを理由に解除時間を累計へ戻さない。対象/occurrenceの世代が一致する有効grantを同じ計上scopeへclipし、対象削除後/時間外の古いgrantを別の対象の控除に使わない。

以下の正値例は、計上可能な制限区間と解除境界が既知という計算fixture。現adapterが実遮断の区間を計測できたという実機合格宣言ではない。

| 条件（指定のない例は21〜23時の制限適用を確認済み） | 期待する既知の制限時間 |
| --- | --- |
| 21〜23時、as-of21:45 | 45分。残り75分を先に計上しない |
| 21〜23時に21:30〜22:30の別rule/別対象を追加、as-of23:00以降 | 21〜23の2時間。アプリ数倍にしない |
| 21〜23時の間に5分解除、その開始/再制限を確認 | 115分。解除5分は累計・週・月・日すべてから除外 |
| 5分の解除要求を2分で早期終了、直ちに再制限を確認 | 118分。要求した5分を控除しない |
| A解除21:30〜21:35、B解除21:32〜21:37 | 解除unionの7分を除き113分。10分を重複控除しない |
| A/B制限中、Aだけ21:30〜21:35解除 | 115分。Bが継続中でも5分を累計へ含めない |
| 解除期限21:35、実際の再制限確認21:37 | 確認21:37まで計上を再開しない。確認できない境界はpartial |
| 制限適用確認21:05、23時終了 | 115分。21:00〜21:05を設定だけから補わない |
| 理由入力/確認取消、解除未実行・制限継続を確認 | 120分。理由入力や取消を解除時間として引かない |
| 22時に停止、22:30再開、23時終了 | 90分 |
| 21:30に21〜23を22〜23へ編集 | 変更前30分＋変更後60分＝90分 |
| 21:30〜22:15の記録欠損 | 既知75分＋partial。欠損を0/完全としない |
| 同じfactの再送/再取込 | 値は増えない |
| 61秒と59秒の2区間 | 120秒。表示済み「1分」「1分未満」を再加算しない |

表示は分未満を「1分未満」、分以上は切捨てた時分を使う提案。生の秒数は保持する。日別の丸め値の和と期間合計が異なる場合があるため、期間合計は必ずnativeの正確な合計を使う。

## 2. 記録する事実

旧command/grant eventだけでは過去policyや適用/解除の実際の境界が揃わず、新集計の正本にできない。#97で必要最小の別ledgerを設ける案:

- `sourceID/eventID/sequence`、耐久commit時刻、policy revision、enabledな曜日/開始・終了/日跨ぎ、対象が存在すること、Activation、記録contextのzone/offset、context epoch。
- 制限/解除/再制限のnative操作開始と結果確認時刻、対象集合の不透明な対応/世代、適用結果、grantの不透明ID/実効期限/早期終了、観測範囲。要求時刻だけで解除済み・再制限済みとしない。
- 初期化、policy確定、停止/明示再開、観測した認可によるActivation変更、nativeによるcontext変更を、対応するcontrol commitと同じwriterで記録する。
- 予定callbackだけを記録源にしない。JS停止後も保存済みfactから計算し、Extensionが観測したcontextはnativeで記録する。
- **reason本文、token、実アプリ名、privateな目的の文章を複製しない**。解除区間の控除に必要な最小のgrant/適用結果だけを保持する。理由や操作payloadを削除しても、残す累計に必要な独立ledgerまで失わない。
- 未確定candidate/previewを、確定policyのfactとして記録しない。

解除前の準備は既存の制限区間を維持できるが、unshield操作が始まったら確認前の区間を成功へ加算しない。解除の失敗/不明は元の制限が継続したと推測せずgapとする。再制限は予定期限から自動再開せず、native確認より前を再開境界にしない。再開後の正値にも区間のqualificationが必要。前後のwriter commitに失敗した場合も、欠落を高水位/lossで識別する。初期化・編集・停止・再開・早期終了・callback・kill復旧の全経路を対象にし、P1/P2と既存の安全な停止を壊さない。

sharedの追加outbox→private ledgerの取込は既存のprivate commit→shared ack、eventID重複排除、短いtransactionを再利用する。control/privateのwriterを同時に持たない。将来のschema番号/DDLは #97 の実装PRで決め、現Control6/History3を本設計文書だけで変更しない。

履歴保存の失敗を設定/停止の成功に読み替えない。一方、追加ledgerのpayload失敗だけで安全な停止/再制限を止めない。source高水位とdurableなloss境界で未保存範囲を識別する。容量は既存の明示候補を勝手に倍増せず、combined pending上限やprivate payloadの計上を #97 で検証する。

## 3. coverage / context / as-of

coverageは`recorded / partial / not-recorded / deleted`を区別する。0秒を返すのは、その範囲の計算事実が揃い、該当する有効区間がない場合だけ。記録前/全削除後の未開始を0の成果に見せない。

- privateに取り込めたledgerと確認済みの高水位から`confirmedThrough`を決める。未取込があれば、後続factを未確認のまま現在まで確定扱いにしない。
- **取込遅延と実際のfact欠落は別**。既存の保守的なhistoryIncompleteだけから、欠損時間を推定しない。新ledgerではsourceのsequence/loss境界と、回復できたpendingを識別する。
- timezone変更を観測したら新context epoch。前回観測から変更観測までの不確かな区間はgapとし、変更が実際に起きた時刻を推測して過去へ書き込まない。
- 時計の逆行/大幅な不連続ではepochを切り、不確かな重なりをpartialにする。既知区間を二重加算しない。「累計が絶対に減らない」とは約束しない。
- 未観測のtimezone往復/時計変更を全て検出できる保証はない。実OSの継続状態を観測済みと扱わず、確認範囲を詳細に示す。不確かな区間はpartialとして計上しない。

**確認できる範囲**: 現nativeのown-storeへの要求受理/設定読戻しは、OS全体で連続して遮断できた証明ではない。#97/#131で適用確認の根拠と継続範囲を検証し、`proofScope`を保持する。確認していない時間を成功へ外挿しない。根拠が足りない区間はpartialとして計上対象から外す。本人がその時間に何をしたかを監視/推定せず、理由から活動や生産性を採点しない。

`ownStoreReadback`/`scheduledValidUntil`は点の設定観測/予定であり、それだけで正の実遮断区間を生成しない。始点と終点のreadbackや一回の手動確認も、その間の連続証明へ自動昇格させない。[AppleのManagedSettingsStore](https://developer.apple.com/documentation/managedsettings/managedsettingsstore)も、指定した設定が端末の挙動を支配する保証はないとする。

**正値のqualification gate**: 実遮断として計上できる`proofScope`と、その区間の継続範囲を裏付ける方法が未確定の間、#98の実遮断の正値表示は進めない。#97での遷移ledger/観測方法の調査・記録や#99の明示fixtureとは切り分ける。記録上の制限有効時間というモデル値を別に検証することはできるが、本人指定の指標へ無断代用しない。数学的な完全保証を新要件に加える意味ではなく、現在の証拠の範囲を越えて成功を表示しないための境界である。

1回のprivate read transactionから、固定した`datasetToken={metricVersion,ledgerRevision,historyRevision,asOf,displayTimeZone}`を発行する。指標は`restricted-excluding-unlocks-v1`として旧設定時間のcacheと混ぜない。上部累計と下部期間は同じtokenで返す。新fact/削除/context変更でtokenが無効なら`changed`を返し、上部/下部を一緒に更新する。期間移動だけでは上部の対象範囲を変えない。

## 4. 週/月/日と有界DTO

表示zoneをtokenに固定し、Gregorian、週開始は月曜を推奨する。日付の境界はCalendarから求め、DSTの日を86400秒としない。zoneを変えたら全体を再取得し、古いcursor/tokenを使わない。

- 週: 月曜00:00〜翌月曜00:00、日別最大7bucket。
- 月: 月初00:00〜翌月初00:00、月曜区切りの週行を月境界でclip（最大6行）。月→clipした週→日の順で詳細化する。
- 上部累計: 利用可能な記録開始からas-ofまでの、解除等を除外した既知の制限区間union。選択週/月には依存しない。週/月/日も同じ控除・観測規則を使う。
- 小さな推移: 全記録範囲の有界sample（最大64）。欠損は線を切り、0へ補間しない。TSへ全ledgerを渡さない。
- 各bucketは`from/until/localLabel/knownSeconds/coverage/rangeKey`を持つ。集計DTOに理由/アプリ実名/tokenを含めない。
- 一日の操作履歴は #132 の別API。historyRevision/as-ofが一致しない場合はその事実を示し、同時点だったと断定しない。理由本文は選択後にだけ取得する。

主表示は「制限を続けた時間」、自分の時間の積み重ねを事実として穏やかに伝える。詳細では「一時解除を除いた記録」と確認できる範囲を説明する。解除を失敗/減点と評価せず、点数・順位・連続利用・過剰な祝福を追加しない。不明な値を励ましのために補わない。

例: 月の最初の週が前月の月曜から始まっても、当月分だけを月合計へ入れる。月末/年末を跨ぐ週の全7日を、両月へ丸ごと加算しない。

## 5. 削除と再取込

| 明示操作 | 消すもの | 保持するもの |
| --- | --- | --- |
| 理由のみ削除（既存） | 理由本文 | 操作metadata、ledger/累計、policy/grant |
| 操作履歴と理由の削除（#132） | 操作payload、理由本文 | 対応するcutoffを記録・保持/更新。ledger/累計、policy/grant |
| 全記録と累計の削除（新しい明示操作案） | 上記＋ledger payload/集計cache/coverage | 全sourceのcutoffを記録・保持/更新。safety metadata/tombstone、policy/grant |

新操作は削除前に「累計も消える」ことを示す。既存ボタンの意味を黙って変更しない。sharedの各source高水位をlock外で取得し、privateの削除/cutoff/cache無効化を一つのwriterでcommitする。古いoutbox・旧token・画面cacheから復活させない。

全削除後は「削除後の記録なし」。有効設定を保ったまま、現在policy/Active grant/再制限未確認/制限の確認範囲を新しいnative baseline factとして記録する。削除時点で続く解除・再制限待ちは新baseline以後も控除/gapを継続し、削除を加算再開の契機にしない。将来の正値にもqualificationを要求する。記録のためにOS制限やgrantを変更しない。baselineを書けなければ未記録として示し、削除前のpolicy履歴を持ち戻さない。異なるsourceIDへ古いcutoffを適用しない。SQLiteページ/WAL/backupからの法科学的消去は保証しない。
