# 時間帯・競合・一時解除のルール

状態: **設計採用済み・実装の検証範囲は下記、実機未検証**（[PR #36](https://github.com/kzk-maeda/itoma/pull/36)、2026-11-06 JSTにmainへマージ）。[了承コメント](https://github.com/kzk-maeda/itoma/pull/36#issuecomment-6685704584)。Issue [#23](https://github.com/kzk-maeda/itoma/issues/23)、[ADR 0004](../adr/0004-rule-precedence.md)。根拠: [利用者回答](https://github.com/kzk-maeda/itoma/issues/23#issuecomment-6654535064)。以下の合意事項、P2修正、未確定の細部を区別する。

## 合意済みの要件

- 日跨ぎは開始日の曜日。平日21時〜翌2時なら金曜夜→土曜2時を含み、日曜夜→月曜2時は含まない。
- 重複時や解除中のルール変更は検知して優先を提案する。利用者に黙って決定しない。
- 一時解除のデフォルトを設定できる。初期値5分、上限30分。
- 理由は空欄不可。本人が文章を考えて入力する。ダミー金額を選択する体験を用意し、請求しない。
- 他の有効ルールが残る場合はそのルールの制限を維持し、理由を表示する。
- 時間帯は端末の現地時刻に合わせる。

## 時間区間の仕様提案

Ruleは曜日集合、startMinute、endMinute、endDayOffset(0/1)を持つ。26:00は翌02:00へ正規化。区間は **[開始, 終了)**、長さは0超〜24時間以内。開始=終了を暗黙に終日とはせず、翌日終端として明示した場合だけ24時間を表す。

ルール評価はUTCの現在instantと、評価時点の端末timezone/暦から現地occurrenceを生成する。同じ日跨ぎoccurrenceを本日開始分と前日開始分で二重計上しない。occurrenceKeyはruleID/version・開始日・timezone・解決済み開始instantから作る。

DSTの不存在境界は次の有効時刻へ進める案、重複境界は開始を早いinstant・終了を遅いinstantへ解決する案とする。解決後に開始>=終了ならそのoccurrenceを無効として通知し、24時間へ丸めない。これはFoundation既定動作の説明ではなく、実装で明示・検証する選択。

## 重複の選択肢と推奨

| 案 | 評価 |
| --- | --- |
| 常に厳しいモード | 分かりやすいが、本人に提案・選択してほしい回答を満たさない |
| 新しいルールを常に優先 | 既存制限を暗黙に弱める可能性がある |
| 各ルール対に個別優先 | 柔軟だが循環と対象ごとの不整合が生じやすい |
| **全ルールの明示的な優先順** | 推奨。循環のない一意な順序で対象ごとの勝者を決め、本人が編集時に確認 |

重複とは「共通する不透明なアプリトークンがあり、曜日・時間区間が重なる」こと。初版はアプリ単位とし、カテゴリ/サイトの包含関係の判定は追加スコープ。

新規/編集時に重複対象・時間・現在の優先順・解除への影響を提示する。新規ルールは既存を優先する順を**提案**し、確定操作を必要とする。モードを勝手に強弱順にせず、並べ替えを許す。重複確認後に他の更新があればrevision不一致として再確認する。

実行時には対象ごとに有効なルールをpriorityOrderで選ぶ。勝者が一時解除不可なら、下位ルールのgrantで解除できない。停止したrule以外の有効な制限は残す。順序欠損/破損は暗黙のモード優先へ置き換えず、last-valid snapshotがあればそれを復旧候補にし、なければ既存OS設定を推測で変更せず不明と表示する。

この順序はルール全体に共通。対象ごとに逆の優先を設定したい要求が出たらルール分割または別設計で扱う。

## 解除と優先順の変化

- grantは対象アプリ1つ、勝者rule/version、現occurrenceにだけ有効。
- 受理時に次の優先ルール切替/現occurrence終了を求め、解除期限の上限として事前表示する。5分を選んでも2分後に別の優先ルールが始まるなら「最大2分」と明示して確定する。
- 同じ対象の解除中に、編集で勝者や対象ruleVersionが変わる場合は、解除終了・残る制限を確認してから更新する。
- 優先ルール切替・対象rule変更・認可喪失で無効化されたgrantは、後で下位ルールに戻っても復活しない。再解除には新しい本人操作が必要。
- **現在の勝者が同じでも、残り解除期間内の未来の切替を比較**する。編集後のnextWinnerChange/occurrenceEndと現在のeffectiveExpiresAtを比較し、短くなる場合は旧/新の終了時刻・理由を提示して本人確認する。
- 実効期限は `min(変更前effectiveExpiresAt, initialExpiresAt, 編集後の次の勝者切替, 現occurrence終端)`。initialExpiresAtは受理時の上限として不変、effectiveExpiresAtは同一grant内で延長しない。切替を後ろへ動かす/削除しても短縮済みgrantを元の長さへ戻さない。
- 短縮は新しい期限予定を先に登録してから有効化する。登録失敗なら候補編集は未反映とし、旧有効policy/実効期限/予定を維持する。登録中は新期限を確定済み残時間として表示しない。
- 現在の勝者/versionも未来の期限も変わらない更新だけ、実効期限を維持する。途中で状態が変わって確認内容と異なる場合は再確認し、本人の確認を使い回さない。

## 初版の方針と残る細部

| 項目 | 提案 | 理由 |
| --- | --- | --- |
| デフォルト解除時間の保存先 | アプリ共通設定、初期5分。1〜30の整数分 | 初版の設定箇所を減らす。変更は新規要求から適用 |
| 解除回数・追加待機 | 初版は追加しない（了承済み） | 本人が選んでいない摩擦を増やさない |
| 理由の空欄 | 前後空白/改行を除いて空なら拒否 | 空白だけで条件を通過しない |
| ダミー金額 | UI設計で候補金額を示して別レビュー | 金額未合意。選択・取消の記録は残すが実決済と混同しない |

## 時計変更・移動

時間帯ルールは現地時刻へ再評価。一時解除はUTCの実効期限を延長せず、timezone変更で再び5分を与えない。timezone変更でoccurrence/勝者が変わればgrantを無効化する。

手動の壁時計変更や再起動をまたぐ改ざん耐性は初版で保証しない。取得できた時刻変更通知で再評価し、nowがacceptedAtより前など矛盾するgrantは不明/要再確認として新しい延長を行わない。プロセスが停止している間の全変更を検出できる前提にしない。期限精度と復旧は #26 で確認する。

## 純粋評価の入出力

Swift共通ドメイン層で、PolicySnapshot・grant集合・now・timezone・Activationを入力し、desiredTargets・各対象のwinningRule・残時間・次境界・無効grantを返す。UIとExtensionは別の優先ロジックを実装しない。OS呼出し・DB更新は評価の外。

### 週次評価の実装契約

[#43](https://github.com/kzk-maeda/itoma/issues/43)の`RuleEvaluator`はgrant適用前の中間結果を返す。API・範囲・エラーは[ItomaCore](../../packages/itoma-core/README.md)を参照。`through`を明示した有限期間内で、対象ごとの勝者/次の勝者変更、全ルールの次境界、保存確認用の重複区間、無効occurrenceを算出する。nilの次境界は期間外も存在しないという意味ではなく、検索終端でも再評価する。重複確認もこの期間とtimezoneに限られ、本人確認・保存やgrantの失効は別の処理。

重複時間はDST解決後の実instantで比較する。通常の壁時計では隣接する区間も、秋の重複時刻では重なることがある。同一ルールの連続した24時間occurrenceがDSTで重なった場合は、新しい開始instantを勝者とし、同じinstantなら新しい開始日を選ぶ。前日分の終了では前日のoccurrenceに戻さない。これは同一ルール内の識別を一意にする補足であり、別ルール間のpriorityOrderやモードの順序を変えない。

認可approvedかつActivation enabledの場合だけ設定上の`desiredTargets`を返し、認可が戻っただけで再開承認待ちを解除しない。認可不明時の空集合は既存OS設定の削除指示ではない。OSの操作可否・観測鮮度・本当の反映結果はcontroller/adapterで扱う。

Swift単体テストはR01/R02、R03の重複情報、R04の勝者選択、R06、R09のNY/Lord Howe/São Paulo/Apia固定instant、R10のtimezone再評価を扱う。R03の保存確認、R04のgrant適用、R10の時計変更時のgrant/復旧と、R05/R07/R08/R11〜R14はこの週次評価だけの検証に含めない。OS予定やiPhoneでの制限成功は未検証。

### 一時解除の評価契約

[#44](https://github.com/kzk-maeda/itoma/issues/44)の`GrantEvaluator`は週次評価を使い、単一対象のPending候補と、Activeなgrantに限った設定上の解除を算出する。未来の勝者切替まで検索し、初期期限を固定して実効期限は短縮だけを許す。失効した記録を引き継ぐことで、下位ルールへ戻った後やtimezone復帰時も再発行しない。

`GrantEditEvaluator`は現在の勝者が同じでも未来の切替を比較し、旧/新期限・理由・本人確認の要否を返す。候補を捨てれば旧有効policy/期限は不変。短縮案と予定登録済みの有効期限は別で、計算だけでは新期限を有効化しない。確認後はsnapshotSequence・候補/入力・現在時刻で影響を再照合する。API・状態別の扱い・残るcontrollerの必須条件は[Package契約](../../packages/itoma-core/README.md#一時解除と編集影響を評価する)を参照。

単体テストはR04/R05/R07/R08/R10/R11/R13/R14の純粋部分と、R12で候補破棄時に旧値を保持することを扱う。本人確認UI、R12の予定登録失敗、R14の登録中の割込みなどのI/O・排他は#47以降で検証する。テストで作ったActiveはOS反映の証拠ではない。
