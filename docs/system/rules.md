# 時間帯・競合・一時解除のルール

状態: **採用提案・レビュー待ち**。Issue [#23](https://github.com/kzk-maeda/itoma/issues/23)、[ADR 0004](../adr/0004-rule-precedence.md)。根拠: [利用者回答](https://github.com/kzk-maeda/itoma/issues/23#issuecomment-6654535064)。以下の合意事項と追加提案を区別する。

## 合意済みの要件

- 日跨ぎは開始日の曜日。平日21時〜翌2時なら金曜夜→土曜2時を含み、日曜夜→月曜2時は含まない。
- 重複時や解除中のルール変更は検知して優先を提案する。利用者に黙って決定しない。
- 一時解除のデフォルトを設定できる。初期値5分、上限30分。
- 理由は空欄不可。本人が文章を考えて入力する。ダミー金額を選択する体験を用意し、請求しない。
- 他の有効ルールが残る場合はそのルールの制限を維持し、理由を表示する。
- 時間帯は端末の現地時刻に合わせる。

## 時間区間の仕様提案

Ruleは曜日集合、startMinute、endMinute、endDayOffset(0/1)を持つ。26:00は翌02:00へ正規化。区間は **[開始, 終了)**、長さは0超〜24時間以内。開始=終了を暗黙に終日とはせず、翌日終端として明示した場合だけ24時間を表す。

ルール評価はUTCの現在instantと、評価時点の端末timezone/暦から現地occurrenceを生成する。同じ日跨ぎoccurrenceを本日開始分と前日開始分で二重計上しない。occurrenceKeyはruleID/version・開始日・timezone・解決済み開始instantから作る。

DSTの不存在境界は次の有効時刻へ進める案、重複境界は開始を早いinstant・終了を遅いinstantへ解決する案とする。解決後に開始>=終了ならそのoccurrenceを無効として通知し、24時間へ丸めない。これはFoundation既定動作の説明ではなく、実装で明示・検証する選択。

## 重複の選択肢と推奨

| 案 | 評価 |
| --- | --- |
| 常に厳しいモード | 分かりやすいが、本人に提案・選択してほしい回答を満たさない |
| 新しいルールを常に優先 | 既存制限を暗黙に弱める可能性がある |
| 各ルール対に個別優先 | 柔軟だが循環と対象ごとの不整合が生じやすい |
| **全ルールの明示的な優先順** | 推奨。循環のない一意な順序で対象ごとの勝者を決め、本人が編集時に確認 |

重複とは「共通する不透明なアプリトークンがあり、曜日・時間区間が重なる」こと。初版はアプリ単位とし、カテゴリ/サイトの包含関係の判定は追加スコープ。

新規/編集時に重複対象・時間・現在の優先順・解除への影響を提示する。新規ルールは既存を優先する順を**提案**し、確定操作を必要とする。モードを勝手に強弱順にせず、並べ替えを許す。重複確認後に他の更新があればrevision不一致として再確認する。

実行時には対象ごとに有効なルールをpriorityOrderで選ぶ。勝者が一時解除不可なら、下位ルールのgrantで解除できない。停止したrule以外の有効な制限は残す。順序欠損/破損は暗黙のモード優先へ置き換えず、last-valid snapshotがあればそれを復旧候補にし、なければ既存OS設定を推測で変更せず不明と表示する。

この順序はルール全体に共通。対象ごとに逆の優先を設定したい要求が出たらルール分割または別設計で扱う。

## 解除と優先順の変化

- grantは対象アプリ1つ、勝者rule/version、現occurrenceにだけ有効。
- 受理時に次の優先ルール切替/現occurrence終了を求め、解除期限の上限として事前表示する。5分を選んでも2分後に別の優先ルールが始まるなら「最大2分」と明示して確定する。
- 同じ対象の解除中に、編集で勝者や対象ruleVersionが変わる場合は、解除終了・残る制限を確認してから更新する。
- 優先ルール切替・対象rule変更・認可喪失で無効化されたgrantは、後で下位ルールに戻っても復活しない。再解除には新しい本人操作が必要。
- 重複するが勝者も対象ruleVersionも変わらない更新では、既存grantの終了日時を維持する。

## 追加の製品判断として提案する値

| 項目 | 提案 | 理由 |
| --- | --- | --- |
| デフォルト解除時間の保存先 | アプリ共通設定、初期5分。1〜30の整数分 | 初版の設定箇所を減らす。変更は新規要求から適用 |
| 解除回数・追加待機 | 初版は追加しない | 未決定の摩擦を勝手に導入しない |
| 理由の空欄 | 前後空白/改行を除いて空なら拒否 | 空白だけで条件を通過しない |
| ダミー金額 | UI設計で候補金額を示して別レビュー | 金額未合意。選択・取消の記録は残すが実決済と混同しない |

## 時計変更・移動

時間帯ルールは現地時刻へ再評価。一時解除は受理時のUTC終了日時を維持し、timezone変更で再び5分を与えない。timezone変更でoccurrence/勝者が変わればgrantを無効化する。

手動の壁時計変更や再起動をまたぐ改ざん耐性は初版で保証しない。取得できた時刻変更通知で再評価し、nowがacceptedAtより前など矛盾するgrantは不明/要再確認として新しい延長を行わない。プロセスが停止している間の全変更を検出できる前提にしない。期限精度と復旧は #26 で確認する。

## 純粋評価の入出力

Swift共通ドメイン層で、PolicySnapshot・grant集合・now・timezone・Activationを入力し、desiredTargets・各対象のwinningRule・残時間・次境界・無効grantを返す。UIとExtensionは別の優先ロジックを実装しない。OS呼出し・DB更新は評価の外。

| ID | 例 | 期待結果 |
| --- | --- | --- |
| R01 | 平日21→翌2、金曜23時/土曜1時/2時 | 前2つは金曜occurrence、2時は区間外 |
| R02 | 同設定で日曜23時/月曜1時 | 区間外 |
| R03 | 同対象・時間重複の新規rule保存 | 優先順の提案と本人確認なしには確定しない |
| R04 | 上位一時解除不可＋下位理由grant | 上位ruleで制限、下位grantは解除根拠にならない |
| R05 | 解除5分要求、2分後に上位rule開始 | 事前に最大2分を表示し、開始境界で下位grant失効 |
| R06 | 上位rule停止、下位ruleまだ有効 | 下位ruleを評価し、制限が残る理由を表示 |
| R07 | 解除時間を5→10へ設定変更 | 既存expiresAt不変、新要求だけ10分 |
| R08 | 空白理由/31分の入力 | 明示的に拒否。金額選択取消で解除を与えない |
| R09 | DST不存在/重複境界 | 上記方針で具体instantを固定してテスト。OS予定の一致は別PoC |
| R10 | timezone変更・手動時計巻戻し | 現地予定を再評価、既存grantを再発行しない。保証限界を表示 |

表は実装するテスト仕様であり、実行済みテストではない。
