# ルールの優先順位と時間

状態: **提案・未確定**。検討Issue: https://github.com/kzk-maeda/itoma/issues/23。この文書は実装・OS動作の保証ではありません。


## 決定が必要な表

| 条件 | 選択肢 | 判断上の注意 |
| --- | --- | --- |
| 時間帯制限中に解除 | 不許可 / 選択した条件で一時許可 | 利用者への事前説明とOSの実現可能性 |
| 複数ルールが重なる | 厳しい条件 / 優先順位 / 明示的な競合解消 | 暗黙の「強い方」を採用しない |
| 解除中にpolicy変更 | 解除維持 / 終了 / 再確認 | 古いpolicyへの許可を新policyへ流用しない |
| 日跨ぎ・曜日 | 開始日の曜日 / 暦日の区間分割 | 日曜→月曜の具体例で検証 |
| タイムゾーン・DST | 現地壁時計 / 固定基準 | 存在しない時刻・重複時刻・移動を扱う |
| 端末時計変更 | 壁時計 / 経過時間との併用 | 再起動後の基準とOSの制約 |
| 権限取消・再制限失敗 | 表示・再試行・本人による復旧 | 失敗を隠さず、意図しない閉じ込めを避ける |

## 評価契約の提案

入力はpolicy revision、現在時刻と時間基準、解除状態、認可・観測。出力は「望ましい制限状態」と理由。OS適用処理と純粋なルール評価を分離し、同じ入力なら同じ結論を得る案です。Swift/TSのどちらに正本を置くかは責務設計で決めます。

## 決定・テストに必要な例

平日23時〜翌7時、週末を跨ぐ予定、同じ対象への重複ルール、期限と新しい制限開始が同時、解除中の対象変更、時差移動、DST前後、時計の前後変更、kill/再起動後の期限処理。各例の時刻・期待状態・理由を固定してユニットテストへ渡します。

OSイベントが指定時刻どおりに必ず呼ばれるとは仮定しません。論理上の期待、OS上で観測できた精度、復旧時の再評価を分けてPoCで採否を判断します。
