## レビューしてほしい判断（回答済みの質問は繰り返さない）

1. **競合のtotal order**：既存ruleを優先する候補を見せ、自分で順序を確定する形でよいか。対象ごとの逆順は初版対象外。
2. **解除の終端**：5分選択でも2分後に優先ruleが変わるなら「最大2分」と説明し、その境界で終える。編集で終了する場合も先に影響を確認する形でよいか。
3. **構成**：MVC相当・Redux・完全Cleanとの比較を踏まえ、小さいMVVMと共通Swift Domainを採用するか。
4. **保存の複雑さ**：単一共有DBより受渡し処理は増えるが、理由本文を本体専用領域へ分けるか。
5. **保持・容量**：自動の期間削除なしで開始し、80MiB警告/100MiB新規本文・履歴payload停止、本人による削除で回復する案を採用するか。これらは実測値ではなく、初版の有限な予算案。
6. **未確定の摩擦**：初版では解除回数制限と追加待機を入れず、ダミー金額候補はUI設計で提案する扱いでよいか。

7. **未保存編集とOS終了**：通常の戻るは破棄確認し、アプリ切替では保持する。ただしOS強制終了後のDraft復元は初版対象外として説明する案。

これは確認のための比較対象であり、未回答のまま自動採用しない。細部修正で済むものはPR上で変更し、他の設計全体を最初からやり直さない。

## PoCで否定され得る仮説

- App Groups内のSQLiteと短いwriter区間で、本体/Extensionが競合・killから回復できる。
- 共有Swift評価層をExpo Module本体と各Extensionへ無理なく組込める。
- 自分のOS設定の反映を短い同期区間で扱え、観測できる範囲を正直に返せる。
- OSイベントと永続した絶対期限で、本体停止中の再制限が必要な精度で成立する。
- File Protectionとバックアップ除外が全付随ファイルにも適用でき、最初のアンロック前の制約を説明できる。

不成立なら #26 に証拠を残してADRを再検討する。未実施を「Acceptedだから動く」と扱わない。
