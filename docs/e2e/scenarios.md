# シナリオの保守手順

[E2Eの入口](README.md) / [実行手順](runbook.md) / [構成](architecture.md)

## 定義と更新場所

**操作・待機・期待結果の正本は[e2e/tests/smoke.test.mjs](../../e2e/tests/smoke.test.mjs)。** 実行対象のID・名前は[e2e/scenarios.json](../../e2e/scenarios.json)へ登録する。ドキュメントだけを修正してテスト実装済みとは扱わない。

変更は、機能/画面を変える開発agentが同じPRで行う。ルートの[AGENTS.md](../../AGENTS.md#e2e-maintenance)を入口とし、PRテンプレートの「E2Eへの影響」で更新内容または不要な根拠と実行結果を記録する。

手動実行時に選んだworkflow refのテストが使われる。変更したシナリオを実機で試すときは、その変更を含むrefを選び、対応するIPAを指定する。AWSコンソールで別のシナリオを保守する運用にはしない。

## 1. 実装前に影響を判断する

1. 対象の機能・route・画面・state・表示文言・testIDを、上表と実行コードで照合する。新規機能で既存ケースの対象外なら、主要な利用経路と失敗/取消の候補を挙げる。
2. 既存の期待動作が変わる場合は、そのケースを同じPRで更新する。表示変更だけでも、テキストselectorや操作可否、遷移先が変わるなら対象にする。
3. 新しい主要フローが公開端末で試せるならケースを追加する。Screen Timeの実認可/実制限など現在の範囲外なら、実機QAのIssue/手順へ紐付け、public smokeを通すための認可迂回やfake成功を作らない。
4. 更新不要なら、どのケースを確認し、なぜ期待結果へ影響しないかをPRへ書く。「見た目だけ」「テストに触れていない」だけを理由にしない。

## 2. 既存ケースを更新する

1. `smoke.test.mjs`の対象IDについて、操作、状態に基づく待機、期待結果を更新する。既存のシナリオIDは意味が同じ間は維持する。名称も変わるなら`scenarios.json`を更新する。
2. `testID`は安定した既存IDを使う。必要なら対象View/操作へ追加する。位置、要素の並び順、長い固定sleepへ依存しない。表示文言の検証が目的である場合は、その文言もassertする。
3. 失敗時の戻り先、キャンセル、保存前/後、未認可/不明を区別する。通過させるためにassertを外したり、skipへ置き換えたりしない。
4. ビルドmarkerやnative構成を変えた場合は新しいIPAを用意する。古いIPAの結果を変更後の合格へ転用しない。

## 3. ケースを追加する

1. `scenarios.json`へ未使用のIDと名前を追加する（例: `DF05`）。削除済みIDを別の意味へ再利用しない。
2. `smoke.test.mjs`へ`test(scenarioName('DF05'), ...)`を追加し、実際の操作と期待結果を記述する。共通のbefore/beforeEach/afterEachを使い、他ケースの実行結果や本人データへ依存させない。
3. この資料の対象表に目的と影響範囲を追記する。ファイルを分割する場合は`e2e/run.mjs`の実行対象と構文検査コマンドも更新する。`tests/`外へhelperを追加する場合は、`e2e/package.json`の`files`に含めて梱包されることを確認する。1jobの10分上限と実行時間を確認し、長い回帰が必要なら短いスモークからの分割を検討する。
4. 登録一覧はNode/Python双方へ渡るため、件数やID集合の判定をそれぞれ書き換える必要はない。登録だけ増やして実装を忘れた場合、未登録のテスト、ID重複、skipは合格にならない。

## 4. 検証してPRへ記録する

```sh
npm run test:device-farm
```

このコマンドは基盤回帰とNode構文検査であり、画面操作を実行しない。加えて[AGENTS.md](../../AGENTS.md#verification)の必須品質チェックと、変更層のテストを実行する。実機E2Eは[実行手順](runbook.md)の手動workflowで行う。push/PRだけでは起動しない。

PRには影響ID・追加/更新または不要な根拠、ローカル結果、Device Farm run/IPA/source SHAを記録する。AWS設定やIPAがなく実機未実施なら、その条件と実行担当が必要な次の操作を明記し、成功とは書かない。ローカル回帰の成功と実機E2Eの成功を分ける。

## 登録と実装を変えるときの注意

`scenarios.json`の削除は期待されるテスト範囲を減らす変更である。機能廃止などの理由と代替の検証をPRへ記録し、人間のレビューを受ける。E2Eの失敗を解消する目的でケースを登録一覧から落とさない。

理由・選択token・本人データをID/URL/ログへ含めない。新しい入力ケースを追加するときは、画像・動画・UI hierarchyに残る内容も確認し、合成データだけを使用する。
